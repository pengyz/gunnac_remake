# gotcha：并行 read_image 的结果顺序不可信

## 现象

t22 考证金钱显示源时，**并行批量 read_image 的返回结果与请求顺序不一致**，且**连续两次错序**：
f2280 帧截图被误配到 f2160 的读数，屏幕数字误读为 **7200**（实为 **6800**，RAM 为准）。
该误判连锁导致 t18 在 `docs/findings/ram-watch-s3.md` §2 记下"金钱不在内部 RAM"的**错误负结果**
（对 12 种编码穷举全部落空的真因：端点值 4400→7200 本身是错的 + 显示尾位 0 是 BCD 真实数位而非字面量）。
t22 以 probe RAM 字节复核纠正，N-0031【证伪撤回】留档（`ram-watch-s3.md` §8.1 更正记录）。

## 为什么

- 图像读取工具的**多图并行响应不保证与请求顺序一一对应**；按"第 N 个结果 = 第 N 张图"消费即埋下错序风险。
- 图像内容本身**没有自描述的帧号绑定**——错序后从像素上无从发现（画面长得都像），只有与
  **字节级证据**（RAM dump / trace / sha）交叉时才会暴露矛盾。
- 项目真值层级（pipeline §2）里截图只是投影：**RAM/ROM 字节才是裁判**；把图像当唯一依据 = 把投影当真相。

## 何时使用

- **一次需要读多张图时**：单张逐次调用，或读前读字节侧证据（`*.ram.hex` / `*.frames.jsonl` / sha256）
  建立"帧号 ↔ 内容"锚点，再用图像仅作展示佐证。
- 数值/状态结论**禁止只凭读图**：必须 RAM/trace 双向印证（同 N-0028 的多证据链形态）。
- 复核历史结论时优先怀疑"端点配对"：两个时间点的读数错位会让一切相邻编码搜索落空。
- 反例（本条教训来源）：并行读 f2160/f2280 两图直接取显示值做 diff 假设。
