# gotcha：限流/基础设施故障 ≠ 四分类差异路由

## 现象

round-008 发生 429 RATE_LIMIT 连环中断：spec-writer（t6）文件已落盘、死于"逐指针终验"阶段；
verifier（t4）死于只读侦察阶段。两者的失败**与产出质量无关**。
若按四分类（移植错→porter / 规格缺口→spec-writer / 投影错误→decomp-analyst / 平台差异→白名单）
去归因，会得出"spec-writer 移植/规格有错"之类的错误结论并错派返工。
round-008 §① 明确记录路由结论：**属基础设施故障，不进四分类（那是差异路由）；纪律上不惩罚成员产出**。

## 为什么

- 四分类回答的是"**门禁红灯的差异**归哪一层修"（pipeline §4）；它的前提是差异真实存在。
- 429/网络/harness 中断没有产生任何差异判断——任务可能死在任意阶段（含只读侦察），
  归因到成员/产出层是范畴错误，还会诱导"改产出""重做任务"的无效返工。
- 处置策略不同：差异 → 派卡修复；基础设施 → **重试或挂起重试**。
  round-008 的调度示范：t6 直接重试续做（产物已落盘，只补终验）；t4 挂起，
  等依赖任务（t3）报 completed 后再 reassign——"现在重试=再烧一轮等待，且限流未缓解"。

## 何时使用

- 成员 turn 异常中断/失败时**先判类**：429、超时、harness 故障 → 基础设施类；
  门禁差异 → 四分类。
- 基础设施类：不惩罚成员产出、不改判定口径；按"产物是否已落盘"决定直接重试（续做）或挂起重试（等依赖）。
- 升级条件（round-008 风险登记）：限流风暴若持续阻塞全部成员 **≥3 轮** → 按 goal 政策考虑 blocked 上报。
- 反例：把 429 死亡记成成员任务 failed 并重派新任务——浪费额度且丢在途产物状态。
